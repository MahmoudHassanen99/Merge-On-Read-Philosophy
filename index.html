The Old Way: Copy-on-Write (CoW)

Think of this like editing a hard-copy book. To change one sentence on page 50, you have to reprint the entire book.

  • !
    High Write Amplification: Changing 1KB might force a 100MB file rewrite.
  • ✓
    Peak Read Speed: Queries are fast because data is pre-merged and organized.
"Prioritize the reader's time over the writer's effort."

The Modern Way: Merge-on-Read (MoR)

Instead of reprinting the book, you just stick a "Post-it" note on page 50 with the correction.

  • ✓
    Instant Ingestion: Just write the "patch" (Delete file in Iceberg / Patch part in ClickHouse).
  • !
    Read Complexity: The database must "merge" the book and the Post-it notes during the query.
"Defer the heavy work until someone actually needs the data."

Why is this better for Big Data?

Streaming Velocity

In a world of real-time events (IoT, Banking, Telecomm), we can't wait for 1GB files to rewrite every second. MoR allows "Append-only" workflows that never stop.

Cloud Economics

On S3 or GCS, rewriting files costs money and I/O. Writing small "deltas" is significantly cheaper and avoids API rate limits during high-frequency updates.

Unified Logic

Whether it's Iceberg's Delete Files or ClickHouse's ReplacingMergeTree, the pattern is the same: Decouple the Update from the Storage.

Key Pointers for Implementation

  • Compaction is Required: You can't have patches forever. Eventually, you must run a "Compaction" job to merge patches into base files.
  • Read vs Write Trade-off: If you need sub-millisecond query responses, use CoW. If you need 100k updates/sec, use MoR.
  • ClickHouse Context: `ReplacingMergeTree` is effectively a "Patching" engine that requires `SELECT ... FINAL` to show the true state.
