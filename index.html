The "Merge-on-Read" Philosophy

Visualizing the architectural shift from rewriting entire datasets (CoW) to incremental patching (MoR).

The Old Way: Copy-on-Write (CoW)

"The Librarian Strategy"

To update a single record, the database must read the entire data file, apply the change in memory, and write a brand new version of the file.

● Write Amplification: 1 row update = 1GB file rewrite.
● Peak Read Speed: Queries are perfectly optimized.

The Modern Way: Merge-on-Read (MoR)

"The Sticky-Note Strategy"

Don't touch the original file. Simply write a tiny "Patch" or "Delete" file on the side. When a query comes, merge them on-the-fly.

● Instant Commits: Optimized for high-frequency streaming.
● CPU Penalty: The query engine must merge data at runtime.

Why Big Data Prefers the "Patch"

Cloud Scale

Object storage (S3/GCS) is immutable. You can't edit a file; you can only replace it. Patching saves millions in I/O costs.

CDC & Streaming

When streaming data from Kafka, waiting for full file rewrites creates huge bottlenecks. MoR allows "Append-Only" flow.

Eventual Compaction

The system cleans up the "Sticky Notes" in the background, turning them into clean books when the system is idle.
